# Обмен с 1С: принимающая сторона

## Состояние на 10.10.2026

Принимающая сторона также перенесена на Windows-сервер `192.168.1.26:8080`; пользователь и настройки сохранены. С Mac протокол проверен через SSH-forward (6/6). Подробности доступа: [migration-windows.md](migration-windows.md). Для удалённого сервера 1С всё ещё нужен внешний HTTPS-адрес либо VPN; локальный адрес не является адресом в интернете.

На локальном Битриксе подготовлены пользователь `exchange_1c` и группа `MIR_SPORT_1C_EXCHANGE`. Пользователь не входит в администраторы. Пароль хранится только в игнорируемом `.env`, ключ `BITRIX_1C_PASSWORD`; логин — `BITRIX_1C_LOGIN`. Технический email `exchange_1c@example.invalid` нужен для обязательного поля Битрикса, не является контактом магазина. Скрипт не отправляет уведомления о создании пользователя.

Адрес для настройки 1С:

```text
http://localhost:8080/local/exchange/1c.php
```

Это дополнительная страница запуска штатного протокола CommerceML. Она подключает штатный обработчик Битрикса, собственного парсера или правок ядра нет. Стандартный `/bitrix/admin/1c_exchange.php` на текущем стенде закрыт для служебного пользователя правами папки админки. Чтобы не выдавать доступ ко всей админке и не менять файлы `/bitrix/`, используется адрес в `/local/`.

Допускается только `type=catalog`; обмен заказами, экспорт каталога и пользовательские справочники через этот адрес выключены. Выгрузку справочников можно добавить после проверки формата реальных данных. Служебная группа разрешена в штатных настройках импорта каталога. HTTPS обязателен для дальнейшего подключения через внешнюю сеть; HTTP в примере предназначен для loopback локального стенда.

`localhost` означает компьютер, на котором выполняется запрос обмена. Если запрос отправляет другой компьютер или сервер 1С, нужен адрес стенда, доступный с него. На GitHub Pages этот адрес работать не будет: там опубликован HTML-прототип, нет PHP/БД.

## Воспроизводимая настройка

```bash
python3 local/tools/setup-1c.py
python3 local/tools/setup-1c.py --apply
```

Без `--apply` скрипт только проверяет состояние. С `--apply` пароль для новой учётной записи генерируется и сохраняется в `.env`, если ключ пуст. В контейнер секрет передаётся через stdin, не через аргументы, не печатается. Повторный запуск не создаёт дополнительных пользователей/групп и не меняет пароль существующей служебной учётной записи. Чужой пользователь с таким логином не изменяется.

Если учётная запись уже существует, а пароль в `.env` потерян, применение останавливается до генерации нового секрета и изменения настроек. Нужно восстановить исходный пароль или отдельно согласовать его смену.

Низкоуровневый `local/tools/setup-1c.php` доступен только в CLI. Настройки и создание группы используют D7; создание пользователя использует `CUser`, потому что установленный `UserTable::add/update` запрещает запись и требует `CUser` для хеширования пароля и событий.

Применённые настройки модуля `catalog`:

| Параметр | Значение |
|---|---|
| Тип инфоблока | `catalog` |
| Сайт | Определяется по активному сайту; на стенде `s1` |
| Характеристики в отдельном инфоблоке | `1C_USE_OFFERS=Y` |
| Принудительное предложение для каждого простого товара | `1C_FORCE_OFFERS=N` |
| Действия с отсутствующими товарами/группами | `1C_ELEMENT_ACTION=N`, `1C_SECTION_ACTION=N` |
| Пропуск единственного корневого раздела | `1C_SKIP_ROOT_SECTION=N` |
| Символьные коды при добавлении / обновлении | `Y` / `N` |
| Интервал / часть файла | 20 секунд / 1 МиБ |
| ZIP / контрольные суммы | Включены |
| Кеш инфоблока | Сброс после завершения (`F`) |

Настройки запрета удаления на стороне Битрикса не заменяют настройку полной выгрузки в самом модуле 1С: поведение нужно проверить с установленной версией модуля. При первом тесте отключить в 1С деактивацию отсутствующих товаров/разделов.

В `docker/mysql/bitrix.cnf` задан `default-time-zone="+03:00"`, чтобы MySQL совпадал с PHP `Europe/Moscow`: иначе штатная проверка соединения возвращала ошибку расхождения времени более 10 минут. MySQL перезапущен; данные не удалялись. В nginx закрыт прямой HTTP-доступ к `/upload/1c_catalog/`, поскольку `.htaccess` не применяется nginx.

## Следующие действия в 1С

Настройка 1С ещё не создана; идентификатор каталога и образец выгрузки не получены. Ни каталог, ни товары этой задачи не импортированы.

1. В установленном модуле обмена для УТ 11.5 создать подключение к сайту. Указать адрес выше, логин из `.env`, пароль из `.env`; выполнить проверку соединения.
2. Включить выгрузку информации о номенклатуре, выбрать нужные цены и склады. Обмен документами/заказами пока не включать.
3. Для одного каталога сайта выбрать произвольную иерархию и создать две верхние группы: «Спорт» и «Рыбалка». Подразделы и распределение реальных товаров согласовать с заказчиком. Дерево формируется на стороне 1С, чтобы следующий обмен сохранял согласованную структуру.
4. Скопировать идентификатор каталога через «Подробно»; предоставить небольшую выгрузку CommerceML с примерами товара с размером/цветом и товара без характеристик.
5. По этому идентификатору настроить привязку инфоблока, свойств SKU и выбранного типа цены к витрине. Сейчас витрина продолжает использовать прежний демо-инфоблок; первичная выгрузка в новый инфоблок сама по себе не переключит её.
6. Проверить создание товаров/предложений, цену и остаток каждого SKU. Повторить выгрузку и убедиться, что дублей нет. Затем проверить изменение цены/остатка и только после этого включать регулярный обмен.

Ручные разделы с выдуманными внешними кодами не создавались: без идентификаторов 1С они могут дублироваться при импорте. Не переименовывать существующие идентификаторы обмена при последующих запусках.

## Проверки

```bash
python3 local/tools/check-1c.py
python3 local/tools/check-1c.py --init-empty
```

`check-1c.py` проверяет отказ анонимному запросу и неверному паролю, вход служебного пользователя, получение сессии протокола и запрет обмена заказами/экспорта каталога. `--init-empty` проверяет разрешение `catalog/init`, но отказывается запускаться, если в локальной папке обмена есть файлы данных: штатный init очищает эту папку. Допускается только штатный `.htaccess` с `Deny from All`.

HTTP-перенаправления отключены, чтобы не передавать авторизацию на другой адрес. `--init-empty` разрешён только для точного адреса текущего Docker-стенда (порт берётся из `HTTP_PORT`); произвольный loopback-адрес не допускается.

На стенде прошли все 7 проверок, повторное применение настройки сохранило те же ID пользователя/группы. Реальная загрузка из 1С, повторный импорт товаров, обновление остатков/цен и расписание не проверены из-за отсутствия источника.

QA: проверки границ доступа — 6/6; каталог, фильтры и корзина — 7/7 при ширине 375 и 1280 px, ошибок страницы/консоли не обнаружено. Бэкенд-ревью: круг 2 — ГОДНО для подготовки принимающей стороны. Отдельно проверены отказ при несовпадающем URL для init и отсутствие изменений при потерянном пароле существующей учётной записи.
